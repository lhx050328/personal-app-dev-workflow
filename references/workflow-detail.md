# 个人应用开发工作流 — 详细操作规范

> 本文档包含7个阶段的完整操作步骤、AI话术模板、输出物要求和完成标准。执行流程前必须通读，执行中随时查阅。

---

## 阶段0：项目初始化 & 环境搭建

### 目标
为新项目建立基础环境和约束规则，确保后续可追踪、可回滚。

### 进入条件
用户表达"我要做一个XXX应用"的想法。

### 操作步骤

1. **项目命名**：根据用户描述，给项目起一个简洁的英文名称（kebab-case，如 `mark-reader`、`word-master`），或让用户自己命名。

2. **创建项目结构**：在用户指定位置（或当前工作目录下）创建：
   ```
   项目名/
   ├── AGENTS.md          # 项目约束文件（含「运行内核」，平台每轮注入、抗压缩锚点①）
   ├── PROJECT-STATE.md   # 项目状态索引（≤40行，AI每轮先读、收尾更新）
   ├── BACKLOG.md         # 需求池（题外想法先入池，不就地扩范围）
   ├── CHANGELOG.md       # 版本日志（每版增改修/回退都记）
   ├── DECISIONS.md       # 关键决策记录(ADR)
   ├── docs/              # 文档目录
   │   ├── 产品设计文档.md
   │   ├── 技术方案文档.md
   │   └── decisions/     # 重大决策的展开材料（可选）
   ├── src/               # 源代码目录
   └── tests/             # 测试目录
   ```
   其中 PROJECT-STATE/BACKLOG/CHANGELOG/DECISIONS 统称**档案四件套**，第5步从 `assets/` 对应模板复制生成。

3. **初始化Git仓库（Windows 本机走双通道工具 egit）**：
   - 先确认 `egit` 可用（不可用按 SKILL.md「Windows 环境 Git 双通道铁律」第5步部署）
   - 执行 `egit init -b main`（等价 git init，默认分支 main）
   - 创建 `.gitignore`（忽略 node_modules、.env、dist 等）
   - 首次提交：`egit add -A` 后 `egit commit -m "项目初始化"`（egit commit 已自动 add，可直接提交）
   - 注意：在 agent 通道、%TEMP% 之外（如 E 盘）直接用官方 `git add/commit` 会因对象只读改名被拦截，**写操作一律用 egit，不要先试官方 git 再回退，直接用**；读操作（log/status/diff/fsck）仍用官方 git

4. **生成AGENTS.md**：从 `assets/AGENTS.md.template` 复制模板，填充项目名称、描述、初始功能设想等内容。**模板顶部的「运行内核」区块必须原样保留并填好**——它随系统每轮注入、不被对话压缩，是长对话后 AI 自恢复的第一锚点。明确写入AI强制行为规范：
   - 每次改动完成后必须创建git commit
   - 每次写完代码必须自我运行验证，报错则自我修复
   - 每次改动后必须编写或更新相关测试
   - 不擅自添加超出MVP边界的功能
   - 每个阶段结束必须等待用户确认

5. **生成档案四件套**：从 `assets/` 复制 `PROJECT-STATE.md.template / BACKLOG.md.template / CHANGELOG.md.template / DECISIONS.md.template` 到项目根，并去掉末尾 `.template` 后缀（即得到 `PROJECT-STATE.md` 等正确 .md 文件名）；PROJECT-STATE 先填好顶部"AI续作必读自举区"和基本盘（项目名、当前=阶段0、下一步），其余随流程推进更新。四件套是"对话之外的项目记忆"，抗上下文压缩主要靠它们（详见文末专题A）。

6. **首次commit**：用 egit 将AGENTS.md、四件套和项目结构提交（`egit commit -m "项目初始化"`），打标签 `egit tag v0.1-init`。

### AI话术模板
```
好的，我们来做一个[应用类型]。

【阶段0：项目初始化】
- 项目名我建议叫 `[英文名]`，可以吗？
- 项目结构我会这样建：[简述结构]
- AGENTS.md我会这样写：[简述核心约束]
- Git仓库会初始化在项目文件夹里

确认没问题的话我就开始初始化。
```

### 输出物
- 项目文件夹 + 完整目录结构
- AGENTS.md（已填充初始内容，含「运行内核」）
- 档案四件套：PROJECT-STATE.md / BACKLOG.md / CHANGELOG.md / DECISIONS.md
- 初始Git版本（tag: v0.1-init）

### 完成标准
用户说"确认"，项目结构、约束文件、四件套无误。

## 阶段1：需求澄清 & 产品设计

### 目标
把模糊想法变成清晰的产品定义，明确做什么、不做什么。这是整个流程最核心的环节，宁可多花几轮对话，也不能跳过。

### 进入条件
阶段0完成，用户确认项目初始化。

### 操作步骤

#### 第一步：场景提问（禁止抽象问题）

先问2-3个具体的场景问题，帮助用户挖掘真实需求。

**AI话术模板**：
```
为了更好地帮你设计这个[应用类型]，我先了解几个具体问题：
1. 你平时在什么场景下会用这个东西？（比如通勤路上、晚上睡前、学习时）
2. 你现在是怎么解决这个需求的？最烦的地方是什么？
3. 你希望用了它之后，最直观的改善是什么？
```

根据用户回答，可追加1-2个更深入的场景问题。

**禁止问的问题**：
- "你的核心需求是什么？"（太抽象）
- "你想要哪些功能？"（用户可能说不清楚）
- "你对这个产品有什么想法？"（太宽泛）

#### 第一步半：产品侧轻量竞品调研（S1，按需深度）

给 MVP 建议前，先用搜索工具快速看有没有同类产品、别人怎么做（不限于应用商店、知乎、GitHub、产品社区）：
- 有没有同类？代表产品是谁？
- 别人怎么解决同一痛点？有哪些可借鉴、哪些坑要避开？（来源记下来，写进产品文档"竞品参照"）
- 我的差异点是什么？

个人小工具 1-2 条点到为止；面向多人或可能商业化的项目再加深。**确无同类也要写明"已检索、无成熟同类，自研"，不凭空假设。**

#### 第二步：AI给出MVP功能建议

基于场景提问的回答，给出一版最小可用产品（MVP）的功能建议清单。功能要少而精，只保留最核心的。

**AI话术模板**：
```
基于你的回答，我建议第一版（MVP）做以下功能：

【核心功能（必做）】
1. [功能1] —— 解决[什么问题]
2. [功能2] —— 解决[什么问题]
3. [功能3] —— 解决[什么问题]

【建议暂不做的功能（后续迭代再加）】
1. [功能A] —— 原因：[复杂度高/非核心/可替代]
2. [功能B] —— 原因：[...]

【技术注意点】
- [如编码格式、性能限制、兼容性等]

你看这个方向对吗？哪些功能要加、要砍、要改？直接说就行。
```

#### 第三步：用户做加减调整

用户在AI建议的基础上做加减。AI要逐条记录，并补充技术影响。

**AI行为规范**：
- 用户要加功能时，提醒："这个功能会增加[X]复杂度，预计多花[Y]时间，确定要加进第一版吗？"
- 用户要砍功能时，确认："砍掉这个功能后，[某个场景]会受影响，能接受吗？"
- 始终引导用户做减法，MVP越小越好。

#### 第四步：整理产品设计文档

当功能范围稳定后，从 `assets/product-design-doc.template` 复制模板，填充内容，生成正式的《产品设计文档》，存入 `docs/产品设计文档.md`。

文档必须包含：
- 产品定位（一句话描述、目标用户、使用场景）
- 核心功能列表（带优先级）
- 本次明确不做的功能（带原因）
- 成功标准（可量化的验收标准）
- 技术约束与注意点

#### 第四步半：价值倒推三问（S7，大项目建议做，小工具可跳过）

文档定稿前，用三个问题反向检验产品是否立得住，结论写进产品文档：
1. 做完时我会怎么评价它（成功的具体样子）？
2. 最尖锐的质疑是什么？
3. 如果失败，最可能败在哪？

若三问暴露方向问题，回到第二、三步调整，不带着硬伤进入下一阶段。

#### 第五步：用户确认

将文档展示给用户，用户说"确认"后本阶段结束。要修改则回到第三步。

### 输出物
- 《产品设计文档》（存入 `docs/产品设计文档.md`）
- egit 提交：`egit commit -m "feat: 完成产品设计文档"`

### 完成标准
用户明确说"确认"，文档生效。

## 阶段2：成本 & 边界确认

### 目标
明确本次开发的投入和交付终点，防止范围蔓延和算力浪费。

### 进入条件
阶段1的产品设计文档已确认。

### 操作步骤

#### 第一步：成本预估

根据产品设计文档，预估实现这个MVP需要的资源：

**AI话术模板**：
```
根据产品设计文档，我预估一下这个项目的投入：

- 预计开发轮次：[X]轮对话（每个模块[Y]轮）
- 预计总时间：[X]小时（纯开发时间，不含你确认等待的时间）
- 模块拆分：
  1. [模块1] —— 预计[X]轮
  2. [模块2] —— 预计[X]轮
  3. [模块3] —— 预计[X]轮

这个投入你觉得可以接受吗？如果觉得太多，我们可以再砍功能。
```

#### 第二步：判断是否需要Demo

**判断标准**：看后端实现成本。
- 后端成本高（涉及文档处理、搜索、大模型调用、数据库等）→ **建议先做前端Demo**
- 后端成本低（纯前端展示、本地交互）→ **可跳过Demo，直接做完整实现**

**AI话术模板**：
```
关于是否先做Demo：
- 这个项目的后端实现成本[高/低]，因为[原因]
- 我的建议是：[先做Demo / 直接做完整实现]
- Demo的意思是：只做前端界面和交互，数据用假的模拟，不做真实后端逻辑。目的是先确认界面和交互顺不顺手，再投入做后端。

你觉得呢？
```

#### 第三步：确认交付终点

明确本次开发做到什么程度算完成：

**可选交付终点**：
- A. 只做前端Demo（HTML+交互+假数据）
- B. 完整前端（真实交互+本地数据存储）
- C. 前后端完整（有服务端、数据库、真实API）

**AI话术模板**：
```
确认一下本次的交付终点：
- [ ] A. 只做前端Demo（界面+交互+假数据）
- [ ] B. 完整前端（真实交互+本地存储）
- [ ] C. 前后端完整（服务端+数据库+API）

我建议选[X]，因为[原因]。你定一个。
```

#### 第四步：更新AGENTS.md

将确认后的成本边界、交付终点、是否做Demo等信息更新到AGENTS.md的"项目边界"部分。然后commit。

### 输出物
- 更新后的AGENTS.md
- egit 提交：`egit commit -m "docs: 更新项目边界与成本约束"`

### 完成标准
用户说"确认"，边界锁定。后续如需变更范围，必须重新走本阶段。

## 阶段3：技术方案设计

### 目标
确定怎么实现，用什么技术，拆成哪些模块。

### 进入条件
阶段2完成，边界已确认。

### 操作步骤

#### 第〇步：技术外部调研（F7，强制，先于选型）

**做技术选型前必须先主动检索前人经验，不凭空造轮子**（用搜索与代码托管平台，不限于 GitHub）：
1. 定检索词：核心功能英文名 + 现成库/算法/最佳实践/标准（如 `large txt file parser javascript`、`localstorage vs indexeddb`）。
2. 列候选对比：候选方案 | 来源链接 | 活跃度/成熟度 | 采用/借鉴/弃用及原因。
3. 下"复用 vs 自研"结论：成熟库能直接用就不自研；要改造说明改什么；确无合适方案才自研并注明"已检索"。
4. 来源与结论填入技术方案文档第〇节「调研与可复用资产」，保证可追溯；关键取舍同时在 DECISIONS.md 记一条 ADR。

规模分级：个人小工具检索 2-3 个候选即可；涉及数据安全、复杂算法或多人使用的，扩大检索并记录关键依据。

#### 第一步：技术选型

根据产品需求和交付终点，给出技术选型方案。对于个人项目，尽量用最简单的技术栈，减少配置和依赖。

**AI话术模板**：
```
技术选型方案：

- 前端：[如 纯HTML/CSS/JS / Vue / React] —— 选择原因：[简单/生态好/适合个人项目]
- 后端：[如 无（纯前端）/ Node.js / Python Flask] —— 选择原因：[...]
- 数据存储：[如 浏览器LocalStorage / JSON文件 / SQLite]
- 构建工具：[如 无 / Vite]

对于个人项目，我建议尽量用最简单的技术栈，减少配置和依赖。你看这个选型可以吗？
```

#### 第二步：模块拆分

将产品功能拆成独立的开发模块，每个模块可独立开发、独立测试、独立commit。

**输出格式**：
```
模块拆分：

| 模块 | 包含功能 | 依赖 | 预计轮次 |
|------|---------|------|---------|
| M1 基础框架 | 项目结构、页面布局、样式基础 | 无 | 1 |
| M2 [功能模块1] | [具体功能] | M1 | 2 |
| M3 [功能模块2] | [具体功能] | M1 | 2 |
| M4 [功能模块3] | [具体功能] | M2, M3 | 1 |
| M5 整体联调 | 模块整合、整体测试、优化 | 全部 | 1 |

开发顺序：M1 → M2 → M3 → M4 → M5
```

#### 第三步：文件结构规划

给出具体的文件目录结构，与阶段0创建的结构对应。

#### 第四步：生成技术方案文档

从 `assets/tech-design-doc.template` 复制模板，填充内容，生成《技术方案文档》，存入 `docs/技术方案文档.md`。然后commit。

#### 第五步：用户确认

将技术方案展示给用户，用户确认或调整。用户不懂技术没关系，用大白话解释每个选择的影响。

### 输出物
- 《技术方案文档》（存入 `docs/技术方案文档.md`）
- egit 提交：`egit commit -m "docs: 完成技术方案文档"`

### 完成标准
用户说"确认"，技术方案锁定。

## 阶段4：产品实现（迭代式）

### 目标
按模块逐步开发，每步自测，每步commit，确保质量和可回滚。

### 进入条件
阶段3完成，技术方案确认。

### 操作步骤（每个模块重复以下流程）

#### 第〇步：原型前置与测试点先行（S2，界面类模块）
- **界面先出原型**：涉及界面的模块，先用静态 HTML/线框图把布局和主交互摆出来给用户看一眼、确认顺手，再写真实逻辑，避免写完大改；纯逻辑/后端模块可跳过。
- **先列测试点再写实现**：动手前用三句话列清本模块测试点——正常流程怎么走、异常输入怎么处理、边界在哪（空数据、大文件、超长文本等），实现完逐条对照验证。

#### 第一步：开发当前模块

按照技术方案的模块顺序，开发当前模块。开发时：
- 严格遵循AGENTS.md中的规范
- 不擅自添加超出MVP范围的功能
- 代码注释清晰，关键逻辑说明

#### 第二步：自我验证与修复（核心环节）

这是区别于"AI写完就交"的关键步骤。必须：

1. **运行代码**：实际运行当前模块的代码（通过终端、浏览器、或代码执行工具）
2. **检查报错**：如果有报错，读取错误信息
3. **自我修复**：根据报错信息，自己修改代码
4. **再次运行**：修改后重新运行，确认报错消除
5. **功能验证**：不仅要"不报错"，还要验证功能是否符合产品设计文档的要求
6. **循环**：重复运行-修复，直到功能正常、无报错

**AI行为规范**：
- 禁止说"代码应该没问题"，必须实际运行验证
- 禁止把报错直接丢给用户，必须先自己尝试修复
- 修复超过3次仍未解决，再向用户说明情况并请求帮助
- 每次修复后都要重新运行完整验证

#### 第三步：编写/更新测试

为当前模块编写测试用例，确保：
- 正常流程能跑通
- 异常输入有处理（如空文件、错误格式）
- 边界条件有覆盖（如大文件、超长文本）

#### 第四步：Commit

当前模块开发、自测、测试都完成后（Windows 本机写操作用 egit）：
```
egit commit -m "feat: 完成[模块名]，包含[功能简述]"
```
（egit commit 会自动 `git add -A`，尊重 .gitignore；读历史用官方 `git log`）

#### 第五步：向用户汇报

告诉用户当前模块完成，展示：
- 做了什么
- 自测结果（跑了哪些测试，是否通过）
- 当前效果（截图或代码片段或运行结果）
- 下一步要做什么

### 用户操作
可以随时叫停、修改、回滚到上一个commit。

### 输出物
- 可运行的代码（存入 `src/`）
- 测试用例（存入 `tests/`）
- 每次commit的版本记录

### 完成标准
所有模块开发完成，AI自测全部通过，每个模块都有对应的commit。

## 阶段5：验证 & 交付

### 目标
最终质量把关，交付成品。

### 进入条件
阶段4完成，所有模块开发完毕。

### 操作步骤

#### 第一步：全流程自检 + 发布检查清单（S4）

把整个应用的所有功能完整跑一遍：
- 每个核心功能都测试到
- 正常流程、异常流程、边界条件都覆盖
- 性能检查（加载速度、响应时间）
- 确认无阻断性bug

**发布检查清单（逐项打勾，缺项不发布）**：
- [ ] 产品设计文档的每条成功标准都已验证
- [ ] 控制台/终端无报错；核心流程在干净环境能从零跑通
- [ ] 版本号已按 SemVer 确定；CHANGELOG 已写本版 Added/Changed/Fixed
- [ ] 代码与四件套已全部 commit，待打 release 标签
- [ ] 使用说明写清"怎么打开、怎么用、已知限制"
- [ ] 回滚预案明确：上一稳定版本标签是什么、出问题怎么退（见专题B）

#### 第二步：生成使用说明

编写《使用说明》：
- 怎么打开/运行这个应用
- 每个功能怎么用
- 已知的限制和注意事项
- 后续可以扩展的方向

#### 第三步：提交用户人工验证

将成品和使用说明交给用户：

**AI话术模板**：
```
所有功能开发完成，我已经全流程自检通过。

请你实际使用一下，重点验证：
1. [核心功能1]是否符合预期
2. [核心功能2]是否符合预期
3. 有没有明显的bug或不顺手的地方

发现问题直接告诉我，我来修复。
```

#### 第四步：问题修复与回归

用户发现问题后：
1. 记录问题清单
2. 逐个修复
3. 修复后回归测试（确保修复没引入新问题）
4. 每次修复都commit
5. 修复完成后重新提交用户验证

#### 第五步：最终交付（渐进验证 S5）

**渐进验证阶梯**：模块自测 → 全流程自检 → 用户小范围试用 → 正式交付，逐级放大，不在没经过小范围验证时直接宣布完成。

用户验收通过后：
- 把 CHANGELOG 的「未发布」块改写成正式版本块（版本号+日期，条目关联 BACKLOG ID）
- 最终 egit 提交（`egit commit -m "release: vX.Y.Z"`），打版本标签 `egit tag vX.Y.Z-release`（标签号与 CHANGELOG 版本严格一致）
- 更新 PROJECT-STATE 为"已交付/维护态"，BACKLOG 已做项移入"已发布归档"
- 整理最终文件结构
- 交付完整产品 + 使用说明 + 版本记录

### 输出物
- 最终产品（完整可运行代码）
- 使用说明文档
- Git版本记录（tag: v1.0-release）

### 完成标准
用户说"验收通过"。

## 阶段6：维护与持续迭代闭环（交付后的常态）

### 目标
让产品像真实商业产品一样持续演进：每个版本可回看、可回退、有规划地进入下一循环，而不是"交付即结束"。

### 进入条件
某版本已打 release 标签交付，项目进入**维护态**；用户提出新需求、优化、bug，或 AI 主动发现问题。

### 操作步骤

1. **一切输入先入 BACKLOG**：新需求/优化/bug/题外想法都先在 BACKLOG.md 登记（编号、类型、来源、优先级），不就地扩大当前工作范围。
2. **按变更双通道分流（F5，AI 自动判断、用户无需记规则）**：
   - **补丁通道**（bug 修复、文案、小优化，不改产品形态）：定位根因 → 最小修复 → 自测与回归 → **PATCH +1**（1.0.0→1.0.1）→ CHANGELOG 记 Fixed → 打补丁标签。不必重走全流程，但"实际运行验证、commit、留痕"一步不能少。
   - **完整循环**（新功能、体验改动、架构调整）：**回到阶段1，重走需求→边界→技术(先调研)→实现→验证全闸门**；向后兼容 MINOR +1（1.x），不兼容/颠覆 MAJOR +1（2.0.0）。
   - 拿不准档位时按完整循环（更稳）。
3. **版本号管理（SemVer，AI 自动编号）**：修 bug 动末位、加兼容功能动中位、不兼容大改动首位；标签号与 CHANGELOG 版本严格一致。
4. **每次改动都 commit**，保持版本可追踪、可回退（回退操作见专题B）。
5. **发布复盘（S6）**：每个版本交付后用三五句话复盘——这版解决了什么、遗留什么、下一版最该做什么，结论写进 CHANGELOG/DECISIONS，并据此重排 BACKLOG 优先级，进入下一循环。

### 输出物
- 新版本产品（补丁或完整循环产物）
- 同步更新的四件套与 docs
- 一条复盘记录与下一循环的 BACKLOG 排序

### 完成标准
本次变更经用户验收、版本入库、四件套同步、复盘完成；项目保持维护态，等待下一循环。

## 专题A：抗上下文压缩与冷启动（F1 落地操作）

**要解决的问题**：对话很长时平台会压缩历史，AI 可能忘掉流程、阶段和早期约定。本工作流不追求"阻止压缩"（平台行为、不可控），只保证**压缩后能无损、快速恢复**。

**三个锚点（按可靠度）**：
1. **项目 AGENTS.md「运行内核」每轮随系统自动注入**（最强，不参与对话压缩）——阶段0 必须写好、后续保持精简。
2. **Skill 与四件套都在磁盘上**：系统每轮常驻技能索引（名字/描述/路径），AI 凭它随时可重新 Read 全文，不依赖是否"记得"。
3. **用户当轮输入永不被压缩**：极端时一句"看下进度、回到流程"即可复位。

**AI 的固定动作**：
- **每轮开工**：先读 PROJECT-STATE.md（≤40 行），据此定位当前阶段/闸门/下一步；不必把所有文档读一遍，按 STATE 指针按需读。
- **即时落盘**：需求确认、技术决策、版本变化一旦发生，立刻写进对应文件（产品/技术文档、DECISIONS、CHANGELOG、STATE），不等对话结束。
- **每轮收尾**：更新 PROJECT-STATE（当前阶段、本轮进展、待确认项、更新时间），回复带位置戳【阶段X/7·状态】。
- **冷启动/新对话接旧项目**：①读 AGENTS 运行内核 + PROJECT-STATE + CHANGELOG 顶部；②输出一段"恢复摘要"（这是什么项目、到第几阶段、已发布哪些版本、上次确认了什么、下一步）；③问清本次意图（继续/加功能/修bug/回退），再按 F2、F5 分流。**禁止从零重来或凭印象编造进度。**
- **感觉自己忘了流程**：立即重读 SKILL.md 与 PROJECT-STATE 再行动。
- **STATE 硬限 40 行**：只放当前态与指针，历史细节沉到 BACKLOG/CHANGELOG/DECISIONS/docs，避免索引本身膨胀。

**诚实边界**：纯逻辑上自指无法 100% 消除；仅当"框架不再注入 AGENTS + AI 不读盘 + 用户完全不语"同时成立才失效，届时用户一句话即可复位。

## 专题B：版本留痕、历史回看与回退（F9 落地操作）

**版本入库节奏**：每完成一个模块或一次重要改动即 `egit commit`；每次正式发布打 `vX.Y.Z-release` 标签并在 CHANGELOG 留版本块。标签、CHANGELOG、STATE 三处版本号必须一致。

**历史回看（读操作，用官方 git）**：
- 看版本时间线：`git log --oneline`；列所有 release：`git tag`
- 看某版改了什么：`git show v1.0.0-release`；对比两版：`git diff v1.0.0-release v1.1.0-release`
- 回看不等于回退，只读不改，随时可查。

**自然语言三档回退（用户说大白话，AI 判断档位并执行；回退不删历史）**：
| 用户的话（示例） | 档位 | AI 动作 |
|------|------|------|
| "刚才改乱了，撤销" | ①撤手头未提交改动 | `git checkout -- .`（或 `git reset --hard HEAD`）回到最近一次 commit |
| "退回上个能用的版本/这版有问题先用旧版" | ②整体退回上一 release | 先 `git branch backup/日期` 留现场，再定位上一个 `*-release` 标签、`git reset --hard <tag>` 切回 |
| "只把某块改回去，别的保留" | ③单模块回退 | `git checkout <tag> -- <文件/模块路径>` 只取回指定部分，其余不动 |

> **回退命令通道（已在 E 盘实测）**：`reset --hard` / `checkout` / `branch` / `show` 只移动分支指针或检出**已有**版本、不产生新的 git 对象，官方 git 在非 TEMP 目录可直接用、不会被拦，**无需走 egit**；只有回退之后要**新建提交或标签**（如记录回退、重发版本）时，那一下 `commit/tag` 才用 egit。

**回退必做的收尾（三档通用）**：
1. 回退后实际运行/冒烟，确认旧版可用；
2. **不删除出问题版本的历史**：在 CHANGELOG 记一条 Rollback（从 v? 退回 v?、原因、受影响 BACKLOG ID），问题版代码保留（分支/标签）待修好重发；
3. 受影响需求在 BACKLOG 退回"已规划"；更新 PROJECT-STATE 当前版本与阶段；
4. 把"为什么回退"在 DECISIONS 记一条 ADR，避免重蹈覆辙。

**兜底**：若 egit 未覆盖某回退命令，让用户在其自己的终端执行官方 git（用户终端不经过 agent 拦截通道），不得静默失败。

## 附录：Git 常用命令速查（Windows 本机：写用 egit，读用 git）

> 为什么写操作要用 egit：见本附录末尾「Git 沙箱拦截专题」。egit 参数与 git 一致，官方 git 能用时它会自动走官方，被拦才切 Dulwich，因此无脑用 egit 做写操作即可。

| 操作 | 命令（写操作走 egit） | 读/查（官方 git，不拦） |
|------|------|------|
| 初始化仓库 | `egit init -b main` | — |
| 查看状态 | — | `git status` |
| 添加所有文件 | `egit add -A` | — |
| 提交（自动add全部） | `egit commit -m "描述"` | `git log --oneline` |
| 打标签 | `egit tag v1.0` | `git tag`（列标签） |
| 查看改动 | — | `git diff` / `git show` |
| 完整性校验 | — | `git fsck` |
| 对比两个版本 | — | `git diff v1.0.0-release v1.1.0-release` |
| 看某版内容 | — | `git show v1.0.0-release` |
| 回滚到上一版 | — | `git reset --hard HEAD~1`（不产生新对象，官方直接可用） |
| 整体退回指定 release | 仅回退后要新建提交时用 egit | `git reset --hard vX.Y.Z-release`（先 `git branch backup/日期` 留现场） |
| 只取回某模块旧版 | — | `git checkout vX.Y.Z-release -- <路径>` |

> 回退的完整判断与收尾（三档、不删历史、同步四件套）见上方「专题B」。

### Git 沙箱拦截专题（Windows agent 通道）

**症状**：`%TEMP%` 之外（E 盘等）执行 `git add/commit` 报
`error: unable to write file .git/objects/xx/<hash>: Permission denied`，而 init/log/status 正常。

**已被实验证伪的方向，不要再试**：磁盘损坏、NTFS 权限、同步盘、第三方杀软、Defender 受控访问、中文路径、autocrlf 行尾、文件内容、`core.sharedRepository` 配置、Junction 联接、把 .git 挪到 TEMP（可行但易失且项目不自包含，已弃用）。

**真正根因**：agent 通道拦截外部进程「临时文件→只读→改名」的类勒索行为序列；git 写松散对象正是此模式（临时文件 chmod 0444 后 rename 成哈希名）。Dulwich（纯 Python git 实现）直接写最终哈希文件（0644、不改名），不触发拦截，产物与官方 git 互通。

**egit 工作机制**：
1. 读命令直接转发官方 git；
2. 写命令先试官方 git，命中拦截特征（Permission denied / unable to write object / failed to insert）自动切 Dulwich 重跑；
3. Dulwich 缺失时自动 `pip install dulwich`；`egit commit` 默认自动暂存全部并尊重 `.gitignore`。

**部署（首次/换机）**：
1. 复制 `assets/egit.py` 到 `C:\Users\<用户名>\bin\egit.py`；
2. 同目录建 `egit.cmd`，内容必须纯 ASCII：
   ```
   @echo off
   python "C:\Users\<用户名>\bin\egit.py" %*
   ```
3. 将 `C:\Users\<用户名>\bin` 加入用户级 PATH；当前会话临时生效：`$env:Path += ';C:\Users\<用户名>\bin'`；
4. 自检：在任意 E 盘目录 `egit init -b main` → 写文件 → `egit commit -m test` → `git fsck` 显示无错即成功。

**兜底优先级**：egit 双通道 → 自动装 dulwich → 引导用户在自己的终端用官方 git（用户终端不经过 agent 通道，无此限制）→ 仍失败如实上报。

## 附录：常见报错处理思路

1. **模块找不到/导入失败**：检查文件路径、文件名大小写、导出方式是否正确
2. **依赖安装失败**：检查网络、换npm镜像源、确认Node版本
3. **端口被占用**：换一个端口，或杀掉占用端口的进程
4. **中文乱码**：确认文件编码为UTF-8，HTML中声明 `<meta charset="UTF-8">`
5. **样式不生效**：检查CSS文件路径、选择器是否正确、是否有缓存（强制刷新）
